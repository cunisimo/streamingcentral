## Hallazgos

### P1 — Sin identidad verificable se habilita el formulario

En `lib/recuperacion.ts`, `leerEnlace` acepta cualquier access_token no vacío con
type=recovery. `sujetoDelToken` devuelve null para un token malformado, y
`decidirPantalla` sólo bloquea la discrepancia si ese sujeto es verdadero.
Por tanto se vuelve a confiar en la sesión anterior cuando falta la identidad.

Ejecutado sobre el módulo del commit, transpilado con TypeScript sin cambios:

```
hash: #type=recovery&access_token=basura
usuarioId: cuenta-A; ready: true
sujetoDelToken: null
decidirPantalla: formulario
```

Control: error=access_denied&error_code=otp_expired con la misma sesión devuelve
error. El arreglo cubre ese control, no todos los enlaces inválidos.
El test «si el token no trae sub, no se inventa una identidad» exige precisamente
formulario con sujeto null: está consolidando la conducta incorrecta.
No implica autenticación de un atacante sin sesión; es una falla de la garantía
de no usar una sesión previa para un enlace no verificado.

**Requerido:** rechazar identidades ausentes/malformadas y vincular el formulario
a la recuperación aceptada por Auth. El texto type=recovery y un JWT decodificado
sin verificar no son, solos, prueba de que Auth aceptó esa recuperación.

### P1 — La identidad se comprueba después de modificar la contraseña

`guardar` en `app/cuenta/reset/page.tsx` llama `updatePassword(pass)` antes de
comparar `usuarioId` con el sujeto esperado. `AuthContext.updatePassword` no
recibe esa identidad esperada y usa la sesión que tenga el singleton Supabase
al ejecutar `auth.updateUser`. Si cambia la sesión entre habilitar el formulario
y efectuar la escritura (por ejemplo, otra pestaña entra en otra cuenta), se
puede modificar esa otra cuenta y recién después mostrar un error.

**Requerido:** ligar la operación a la identidad/sesión de recuperación antes
de escribir, sin depender sólo del estado React ni de una comprobación posterior.
Verificar el cambio de sesión durante la operación con un cliente controlado;
el criterio es cero escrituras sobre la cuenta ajena, no sólo ausencia de éxito.
Esta carrera se identifica por lectura; no se ejecutó contra Auth real.

### P2 — La causa del incidente se afirma con más certeza que la evidencia

El informe y los comentarios dicen que al dueño se le cambió la contraseña de
otra cuenta y que el token ya estaba consumido. La reproducción A/B prueba que
el defecto existe y puede producir ese síntoma. No correlaciona las cuentas,
tokens ni escrituras del intento original. La evidencia original confirma
otp_expired y un login de la cuenta esperada; no demuestra el cambio en otra.

**Requerido:** describirlo como causa reproducida posible del síntoma, sin
afirmar causalidad del incidente individual. Conservar explícitamente pendiente
el rechazo del enlace nuevo. No usar «incidente cerrado» para este arreglo parcial.

atribuir el consumo a un scanner por el mero User-Agent null.
